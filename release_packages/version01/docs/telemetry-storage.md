# Telemetry storage

Alembic revision `0002_telemetry` adds the SQLAlchemy `app.models.Telemetry` model
and PostgreSQL `telemetry` table after `0001_registry`. It implements persistence
for sections 3-5 of the [approved telemetry-batch.v1 contract](Technical_Lead_Telemetry_Ingestion_Contract_Approval_Sprint01.pdf).
The migration is additive and preserves existing registry rows.

## Stored fields

| Column | PostgreSQL type | Rule |
| --- | --- | --- |
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | Internal primary key; not the event identity. |
| `schema_version` | `SMALLINT` | Required, `1`; copied from the batch envelope. |
| `device_id` | `VARCHAR(128)` | Required foreign key to the registered device. |
| `boot_id` | `VARCHAR(128)` | Required nonempty string, including contract values such as `boot-a`. |
| `sequence_number` | `BIGINT` | Required, non-negative. |
| `measured_at` | `TIMESTAMP WITH TIME ZONE` | Nullable physical measurement time. |
| `device_uptime_ms` | `BIGINT` | Required, non-negative elapsed milliseconds; not an absolute timestamp. |
| `gateway_received_at` | `TIMESTAMP WITH TIME ZONE` | Required original gateway receipt time. |
| `backend_received_at` | `TIMESTAMP WITH TIME ZONE` | Required, generated by PostgreSQL with `clock_timestamp()`. |
| `metric` | `VARCHAR(32)` | Required, `temperature` in v1. |
| `value` | `NUMERIC` | Required finite value; returned as Python `Decimal`. |
| `unit` | `VARCHAR(32)` | Required, `celsius` in v1. |
| `quality` | `JSONB` | Required object with `reading: valid` and an approved `clock` value. |

Clock values are `synchronised`, `unsynchronised`, `estimated`, and `unknown`.
Missing/null quality members and unsupported values fail a database check.
Supplied `measured_at` values are preserved for every clock quality, and nulls
remain null. Later history/live processing must decide whether to trust them;
storage does not substitute a receipt timestamp for a measurement timestamp.

The identifier limit and signed 64-bit counters (`0` through `9223372036854775807`)
are explicit storage limits. Boot IDs are case-sensitive strings, not UUID-only
values. `NUMERIC` has no fixed precision/scale, so storage does not round readings
to an arbitrary number of decimal places. Parse decimal JSON numbers without
loss before constructing the model. Sensor-specific value limits belong to
ingestion validation once the sensor range is selected; this migration enforces
finiteness without inventing that range.

## Identity and transactions

`uq_telemetry_identity` enforces
`UNIQUE (device_id, boot_id, sequence_number)` atomically, including concurrent
inserts. Neither timestamp, metric, gateway, nor the internal row ID changes this
domain identity. An insert that reuses an existing identity fails with PostgreSQL
SQLSTATE `23505`, leaving the original row unchanged. Changing any one of the
three identity components permits a distinct event.

The device foreign key uses `ON DELETE RESTRICT`: devices with telemetry cannot
be deleted accidentally along with their history. Disable registry entities to
preserve history. No automatic retention deletion or cascading purge is enabled;
define a retention policy before production volumes accumulate.

The [ingestion service](telemetry-api-contract.md) authenticates the gateway,
checks registry ownership, validates each item, compares immutable fields on
uniqueness conflicts, and returns outcomes only after commit. It uses PostgreSQL
conflict handling and savepoints so permanent item failures do not invalidate
unrelated items. The database constraint alone does not distinguish a matching
retry from conflicting content.

## UTC and timestamp ownership

All three absolute timestamps use PostgreSQL `TIMESTAMP WITH TIME ZONE`, which
[stores instants internally in UTC](https://www.postgresql.org/docs/17/datatype-datetime.html#DATATYPE-DATETIME-INPUT).
Backend SQLAlchemy connections explicitly set `timezone=UTC`, after any supplied
libpq options. The `UTCDateTime` type normalizes timezone-aware Python inputs and
query results to UTC, and rejects naive datetimes. Nonzero offsets preserve the
same instant, including when conversion changes the calendar date.

Raw SQL bypasses Python validation: include an explicit offset in timestamp
literals/bindings. External database clients can display a different local time
according to their session timezone without changing the stored instant.

Writers omit `backend_received_at` so the database supplies its own clock time
at insertion, rather than the potentially earlier transaction start time.
This records backend processing receipt; it does not record commit completion.
The persistence model is a trusted internal interface, not a request schema.
The [request schema](telemetry-api-contract.md) rejects client-supplied
`backend_received_at`; ingestion must never pass arbitrary request fields to the
model. Backend or gateway receipt fields must not be overwritten during
duplicate handling.

## Device/time queries

Two B-tree indexes support bounded per-device range queries and ordered scans:

- `ix_telemetry_device_measured_at (device_id, measured_at)` for physical
  measurement history when a measurement time exists.
- `ix_telemetry_device_backend_received_at (device_id, backend_received_at)` for
  backend receipt history, including events whose `measured_at` is null.

Filter by `device_id` and a bounded range on the corresponding timestamp, and
order by that timestamp with the domain identity as a tie-breaker. These indexes
also cover device foreign-key lookups through their leading column. Receipt
ordering is operational history; it does not define live-alert or cross-boot
measurement ordering. Review query plans against representative data before
introducing production history endpoints.

## Apply and recover

Use the [backend migration commands](../backend/README.md#registry-migrations-and-demo-seed).
From `backend/` with explicit database configuration:

```sh
python -m alembic upgrade head
python -m alembic current
python -m alembic check
```

The head revision is `0002_telemetry`. Run migrations once before enabling a
telemetry writer; no API startup action creates tables or inserts telemetry.
Upgrade creates an empty telemetry table and preserves registry registrations.

On a disposable database, `python -m alembic downgrade 0001_registry` removes
telemetry and its indexes while preserving the registry. This destroys readings;
upgrading again recreates only an empty table. For an existing environment, stop
telemetry writers and take a PostgreSQL backup before destructive rollback.
Recover deleted readings from that backup into a separate database and validate
them before switching consumers. PostgreSQL transactional DDL rolls back a failed
migration; inspect `alembic current` before retrying.

## Verification

Run the [backend PostgreSQL acceptance suite](../backend/README.md#development-checks)
with `REGISTRY_TEST_DATABASE_URL`. Despite its historical name, the variable now
selects the maintenance connection for both registry and telemetry suites. Each
suite creates and removes only its own randomly named database. Missing explicit
configuration fails rather than silently skipping tests.

`tests/integration/test_telemetry.py` covers populated registry upgrade,
telemetry downgrade/re-upgrade, model/migration agreement, duplicate/conflicting
and concurrent identities, each identity component, nullable measurement times,
all clock qualities, offset normalization, rejection of naive timestamps,
database-generated receipt time, required fields and checks, device deletion
restrictions, decimal/counter precision, and device/time indexes and queries.
CI discovers this file in the existing PostgreSQL integration step.

Local verification on 2026-09-25: all 23 registry/telemetry integration tests
passed using the backend container runtime with the working source mounted
read-only and an isolated PostgreSQL 17.11 container. All 13 backend unit tests,
Ruff lint/format checks, offline migration SQL generation, and Alembic model
agreement passed. The temporary databases, container, and volume were removed.
This is local acceptance evidence, not a GitHub Actions run or deployment.
